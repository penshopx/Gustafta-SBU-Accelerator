### Rancangan Konseptual: Penyegaran Deklarasi API Sebelum Pemeriksaan Frontend

**1. Identifikasi Akar Masalah**
Pemeriksaan tipe frontend (`@workspace/gustafta-sbu`) bergantung pada berkas yang dihasilkan (*generated types*) di folder `dist` milik `@workspace/api-spec`. Jika berkas ini tidak diperbarui secara otomatis setelah penggabungan kode atau pada workspace baru, pemeriksaan frontend akan gagal meskipun kontrak `openapi.yaml` sudah benar.

**2. Penyesuaian Alur Persiapan (*Preparation Order*)**
Urutan eksekusi harus diatur secara ketat: **Codegen API Spec -> Typecheck Libs -> Frontend Check**.

*   **`lib/api-spec/package.json`:** Pastikan skrip `codegen` tidak hanya menghasilkan berkas, tetapi juga memverifikasi tipe library (`typecheck:libs`) sebagai satu kesatuan yang utuh.
*   **`scripts/post-merge.sh`:** Tambahkan langkah eksplisit untuk menjalankan `pnpm --filter @workspace/api-spec run codegen` *sebelum* skrip ini memanggil pemeriksaan frontend atau pengujian lainnya.
*   **Alur CI/Pemeriksaan Otomatis:** Pada pipeline validasi, pastikan langkah yang menangani `api-spec` diselesaikan dan artefak `dist`-nya tersedia sebelum langkah pemeriksaan frontend dimulai.

**3. Pembuktian Kondisi Deklarasi Lama (*Stale State*)**
Untuk membuktikan bahwa alur ini bekerja, simulasi harus dimulai dari kondisi "kotor":
*   Hapus atau kembalikan berkas di folder `dist` `@workspace/api-spec` ke versi lama.
*   Jalankan skrip persiapan yang telah diperbarui.
*   Verifikasi bahwa pemeriksaan frontend berhasil tanpa memerlukan intervensi manual untuk menjalankan *codegen* secara terpisah.

**4. Batasan yang Dipertahankan**
*   Tidak mengubah aturan transisi database.
*   Tidak mengubah operasi database.
*   Tidak mengubah kontrak API (`openapi.yaml`).
