Berikut adalah rancangan konseptual untuk mengamankan pemilihan domain Clerk dari manipulasi header proxy (*Host Header Injection* / *Domain Fronting*). 

Sesuai dengan batasan yang telah kita sepakati, ini adalah **usulan desain**, bukan implementasi yang telah diverifikasi. Kode tidak boleh diganti secara mentah tanpa peninjauan terhadap lingkungan deployment aktual (misalnya, bagaimana Replit atau reverse proxy lainnya meneruskan header).

### 1. Sumber Kebenaran (Source of Truth) untuk Domain yang Diizinkan
Daftar domain tidak boleh diambil dari header permintaan secara dinamis tanpa validasi. Daftar ini harus didefinisikan secara statis di lingkungan server.

*   **Variabel Lingkungan:** Tambahkan `ALLOWED_HOSTS` (atau `TRUSTED_DOMAINS`) di `.env` atau Secrets.
*   **Format:** Array JSON atau string yang dipisahkan koma, mencakup domain utama dan semua domain alternatif yang sah.
    ```env
    ALLOWED_HOSTS=["gustafta-sbu-accelerator.replit.app", "gustafta.my.id", "localhost:3000"]
    ```

### 2. Konfigurasi *Trust Proxy* di `app.ts`
Sebelum middleware Clerk berjalan, aplikasi harus diberi tahu secara eksplisit proxy mana yang boleh dipercaya. Jika tidak dikonfigurasi, Express/Node.js akan mengabaikan `X-Forwarded-Host` (yang aman, tetapi mungkin memutus fungsionalitas jika aplikasi memang berada di belakang proxy). Jika dikonfigurasi terlalu longgar (misal: `true`), aplikasi akan percaya header dari klien mana pun.

*   **Tindakan:** Atur `app.set('trust proxy', ...)` hanya ke IP atau subnet proxy yang sah (misalnya, loopback untuk pengujian lokal, atau rentang IP spesifik dari platform hosting). Jangan gunakan `true` di produksi kecuali dokumentasi platform hosting secara eksplisit menyarankannya.

### 3. Logika Validasi di `clerkProxyMiddleware.ts`
Middleware harus menormalisasi dan memvalidasi host *sebelum* mencari publishable key.

**Alur Konseptual:**
1.  **Ekstraksi:** Ambil nilai dari `req.headers['x-forwarded-host']` (jika proxy tepercaya) atau fallback ke `req.headers.host`.
2.  **Normalisasi:** Ubah menjadi huruf kecil dan hapus nomor port jika ada (karena `ALLOWED_HOSTS` biasanya tanpa port, atau pisahkan port dan host).
3.  **Validasi Allowlist:** Cek apakah host yang dinormalisasi ada di dalam `ALLOWED_HOSTS`.
4.  **Penolakan (Fail-Safe):** Jika host **tidak** ada di daftar, tolak permintaan segera (misalnya, HTTP 400 Bad Request atau 403 Forbidden). **Jangan** fallback ke domain default secara diam-diam, karena ini bisa menyembunyikan serangan.
5.  **Pemetaan Key:** Hanya jika host valid, lanjutkan ke logika pemetaan host ke Clerk Publishable Key yang sudah ada.

### 4. Skenario Pengujian (Tanpa Kredensial Nyata)
Pengujian harus membuktikan bahwa header yang dimanipulasi tidak dapat mengalihkan domain autentikasi.

| Skenario Uji | Header yang Dikirim | Hasil yang Diharapkan |
| :--- | :--- | :--- |
| **Positif (Domain Sah)** | `Host: domain-alternatif.sah` | **200 OK** (atau 401 jika belum login). Publishable key alternatif terpilih. |
| **Negatif (Host Asing)** | `Host: evil.com` | **400 Bad Request**. Tidak ada publishable key yang dipilih. |
| **Negatif (Spoofing Proxy)** | `Host: domain.sah` <br> `X-Forwarded-Host: evil.com` | **400 Bad Request** (jika proxy tidak tepercaya) atau **200** (jika proxy tepercaya dan `domain.sah` yang dipakai). `evil.com` harus diabaikan. |
| **Negatif (Format Aneh)** | `Host: domain.sah.evil.com` | **400 Bad Request**. Mencegah *subdomain spoofing*. |

### Catatan Penting untuk Implementasi
*   **Jangan Mengubah Dukungan Domain Alternatif:** Logika pemetaan (mapping) yang sudah ada dan terbukti bekerja untuk domain alternatif yang sah harus tetap dipertahankan. Validasi ini hanya menambahkan "pintu depan" yang memastikan host tersebut memang diizinkan sebelum masuk ke logika pemetaan.
*   **Normalisasi Port:** Perhatikan bahwa `req.headers.host` sering menyertakan port (misal `localhost:3000`), sedangkan `X-Forwarded-Host` mungkin tidak. Fungsi normalisasi harus menangani ini secara konsisten agar tidak terjadi *false negative* pada pengujian lokal.

Rancangan ini siap untuk ditinjau. Jika Anda atau agen pengembang memutuskan untuk menerapkannya, pastikan untuk menyesuaikan konfigurasi `trust proxy` dengan arsitektur jaringan spesifik di mana aplikasi ini di-deploy. Tidak ada kode yang diubah atau tugas yang diambil alih pada giliran ini.
