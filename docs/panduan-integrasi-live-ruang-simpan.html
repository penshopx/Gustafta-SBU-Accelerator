SBU ACCELERATOR · PANDUAN OPERASIONAL

Mengaktifkan dan memverifikasi integrasi live Ruang Simpan

Untuk publisher Gustafta, operator SBU, dan dua pemilik perusahaan yang menyetujui pengujian.

Status: panduan ini bukan laporan keberhasilan. Pemeriksaan terakhir sebelum panduan dibuat masih menemukan HTTP 200 HTML pada endpoint Gustafta. Seluruh hasil live harus diisi setelah benar-benar diuji.

Mulai dari sini

Urutannya: aktifkan endpoint Gustafta → periksa 401 JSON + no-store → verifikasi hubungan dua pemilik → masukkan token melalui Secrets → atur pemetaan per lingkungan → uji live → laporkan hasil tanpa data pribadi.

Jangan: menempelkan token di chat, formulir biasa, frontend, URL, unggahan, source code, terminal yang direkam, atau laporan. Jangan menyalin profil ke database SBU, mengakses dokumen, atau meminta izin tulis.

1. Pembagian tanggung jawab

Jika tidak ada pihak yang memiliki akses publisher, proses berhenti di langkah 2. Tidak ada pemantauan otomatis atau konfirmasi aktivasi yang diterima agen di luar percakapan ini.

2. Aktivasi endpoint oleh publisher

Pesan siap dikirim

Mohon aktifkan GET /api/v1/ruang-simpan/company-profile pada workspace Gustafta yang melayani https://gustafta.my.id. Pemeriksaan terakhir tanpa token menghasilkan 200 text/html dengan private, max-age=0. Respons tanpa token harus 401 JSON dengan Cache-Control: private, no-store. Respons terautentikasi harus objek profil langsung sesuai kontrak; token menentukan pemilik dan hanya izin profile:read yang diperlukan. Mohon konfirmasi setelah versi endpoint tersebut benar-benar dipublikasikan.
  1. Pastikan workspace dan deployment yang diperiksa memang melayani https://gustafta.my.id. Jangan mengganti domain hanya karena tercantum dalam templat yang belum diverifikasi.
  2. Periksa penanganan rute API dan routing proxy. HTTP 200 HTML dapat berasal dari fallback halaman web atau routing deployment yang salah; ini perlu diperiksa, bukan diasumsikan.
  3. Jika ada fallback SPA, rute API harus ditangani sebelum fallback. Rute API yang tidak tersedia tidak boleh diam-diam menjadi halaman HTML.
  4. Endpoint menerima GET tanpa body dan tanpa parameter identitas pemilik. Server Gustafta menentukan pemilik dari token koneksi, memeriksa izin dan status aktif pemilik.
  5. Pastikan respons sukses dan gagal memiliki Cache-Control: private, no-store. Publikasikan perubahan dari workspace Gustafta yang benar melalui publisher yang berwenang.

Pemeriksaan publik tanpa token

Perintah berikut hanya menampilkan status dan header yang diperlukan, tidak mencetak body atau memakai token:

curl --silent --show-error --max-time 20 --max-redirs 0 \
  -o /dev/null -D - \
  -w 'status=%{http_code}\ncontent_type=%{content_type}\n' \
  https://gustafta.my.id/api/v1/ruang-simpan/company-profile \
  | grep -Ei '^(HTTP/|content-type:|cache-control:|status=|content_type=)'

Harus: HTTP 401, Content-Type application/json (boleh disertai charset), dan Cache-Control private, no-store. Publisher juga perlu memverifikasi body benar-benar JSON melalui pemeriksaan server yang tidak memasukkan data sensitif ke laporan.

401 saja belum cukup. HTML, redirect, timeout, atau header tanpa no-store berarti pemeriksaan awal belum lulus. Jangan memasukkan token sampai domain dan kontrak sumber terverifikasi.

3. Verifikasi dua pemilik

  1. Pilih dua pemilik berbeda, beri label laporan A dan B. Gunakan akun uji yang disetujui; jangan menghapus profil perusahaan nyata hanya untuk membuat kasus kosong.
  2. Masing-masing pemilik login ke Gustafta dan menunjukkan secara privat bahwa akun dan profil perusahaan yang akan dibaca memang miliknya.
  3. Masing-masing login ke SBU di lingkungan yang akan diuji. Operator memperoleh ID Clerk dari sesi terverifikasi melalui sarana administrasi yang berwenang, bukan ID yang dikirim sebagai parameter frontend.
  4. Operator dan pemilik mengonfirmasi hubungan akun SBU ↔ akun Gustafta ↔ perusahaan secara eksplisit. Email atau nama yang sama bukan bukti hubungan kepemilikan.
  5. Buat koneksi Gustafta terpisah untuk A dan B dengan profile:read saja. Jangan meminta profile:write, files:read, files:write, atau akses dokumen.
  6. Catat hanya status “hubungan kepemilikan terverifikasi” di laporan. ID nyata hanya digunakan dalam konfigurasi server yang terbatas aksesnya; jangan masukkan ID, nama perusahaan, NIB, alamat, atau token ke laporan.

Respons profil sumber tidak menyediakan bukti bahwa akun Gustafta setara dengan akun SBU. Pemetaan administratif harus diverifikasi sebelum diaktifkan.

4. Secrets dan pemetaan per lingkungan

Di Replit SBU, gunakan Tools → Secrets atau formulir Secrets resmi yang dibuka agen. Untuk aplikasi terpublikasi, periksa dan atur secret production pada pengaturan publishing; jangan menganggap konfigurasi development otomatis cukup untuk production.

Development

  1. Buat secret server RUANG_SIMPAN_TOKEN_OWNER_A_DEV dan RUANG_SIMPAN_TOKEN_OWNER_B_DEV. Masukkan token hanya di alur Secrets. Token harus berbeda, bukan satu token yang diberi dua nama.
  2. Atur variabel server RUANG_SIMPAN_CONNECTIONS untuk development. Contoh di bawah hanya placeholder; ganti dengan ID Clerk development yang telah diverifikasi melalui konfigurasi privat.
{
  "ID_CLERK_A_DEVELOPMENT": "RUANG_SIMPAN_TOKEN_OWNER_A_DEV",
  "ID_CLERK_B_DEVELOPMENT": "RUANG_SIMPAN_TOKEN_OWNER_B_DEV"
}

Production

Verifikasi kembali ID Clerk production dan hubungan kepemilikannya. User store Clerk development dan production terpisah. Gunakan secret khusus production dan pemetaan production tersendiri:

{
  "ID_CLERK_A_PRODUCTION": "RUANG_SIMPAN_TOKEN_OWNER_A_PROD",
  "ID_CLERK_B_PRODUCTION": "RUANG_SIMPAN_TOKEN_OWNER_B_PROD"
}
  • Nama secret harus cocok dengan RUANG_SIMPAN_TOKEN_[A-Z0-9_]+.
  • Nilai pemetaan adalah string nama secret, bukan token dan bukan objek dengan ownerId/token.
  • Jangan gunakan pemetaan shared untuk menggantikan pemeriksaan development/production yang terpisah. Operator perlu memeriksa konfigurasi efektif server API pada tiap lingkungan.
  • Jangan membuat variabel token dengan awalan VITE_; token tidak boleh masuk bundle frontend.
  • Tidak ada fallback ke token bersama. Secret lama RUANG_SIMPAN_TOKEN_SBU tidak membuktikan hubungan dua pemilik.
  • Setelah perubahan development, restart workflow API sekali. Perubahan production perlu diterapkan melalui mekanisme publishing yang sesuai dan dikonfirmasi pada deployment yang berjalan. Jangan menerbitkan produksi tanpa persetujuan pemilik.

Referensi Replit: Secrets. Jika konfigurasi belum tersedia di server API, hentikan tes live; jangan mencetak environment untuk mencari token.

5. Pengujian live

Lakukan pada lingkungan yang disetujui, dengan dua pemilik nyata atau akun uji live yang berwenang. Koneksi, respons, dan akun harus berasal dari sistem yang benar-benar berjalan, bukan stub atau fetch yang diganti mock.

A. Profil sumber langsung dan SBU

  1. Operator menjalankan pemeriksaan terautentikasi server-ke-server untuk A lalu B. Kredensial dibaca oleh server dari Secrets, tanpa dicetak. Jangan menempelkan bearer token pada perintah curl, URL, chat, atau DevTools.
  2. Verifikasi GET sumber memakai Authorization Bearer, tanpa body/parameter pemilik, dengan penolakan redirect dan tanpa cache.
  3. Untuk profil terisi, verifikasi HTTP 200 JSON berupa objek langsung dengan field name, nib, address, revision, updated_at. Revision harus bilangan bulat nonnegatif dan updated_at harus timestamp sah atau null sesuai kontrak.
  4. Bandingkan profil secara privat bersama pemilik. Laporkan hanya “profil sesuai pemilik A/B”, tanpa isi field atau salinan respons.
  5. Login A ke SBU, buka halaman Profil perusahaan, periksa hasil. Ulangi untuk B. Endpoint lokal adalah GET /api/ruang-simpan/company-profile; responsnya {userId, profile}. Identitas respons harus cocok dengan akun SBU aktif.
  6. Periksa no-store pada respons sumber maupun lokal. Jangan membagikan HAR, screenshot profil, atau salinan request yang mengandung cookie, token, ID, atau data perusahaan.

B. Pemisahan akun, reload, dan respons terlambat

  • A → logout → B: data A tidak boleh muncul, termasuk selama pemuatan. Ulangi B → A.
  • Reload saat B aktif: tidak boleh memulihkan profil A. Ulangi untuk A.
  • Buka dua tab, ubah akun di tab kedua, lalu kembali ke tab pertama: tampilan privat lama harus disembunyikan dan identitas diperiksa kembali.
  • Dengan perlambatan jaringan pada akun uji, mulai membaca profil A lalu ganti akun sebelum respons selesai. Hasil A yang terlambat tidak boleh masuk ke tampilan B.
  • Uji Kembali/Maju browser setelah pergantian akun: halaman yang dipulihkan tidak boleh menampilkan profil akun sebelumnya.

Seluruh respons lokal, termasuk kegagalan, harus Cache-Control: private, no-store. Kegagalan setelah sukses tidak boleh menampilkan profil lama sebagai data terbaru.

Bentuk profil kosong yang sah

{
  "name": "",
  "nib": "",
  "address": "",
  "revision": 0,
  "updated_at": null
}

{}, null, HTML, JSON rusak, atau timeout bukan profil kosong sah.

Pengujian kegagalan perlu persetujuan.
  • Gunakan koneksi uji khusus untuk pencabutan; jangan mencabut koneksi operasional milik pelanggan.
  • Kedaluwarsa harus dibuktikan memakai token uji yang benar-benar expired atau dukungan fixture live resmi publisher. Token palsu atau respons mock tidak membuktikan kasus expired.
  • Untuk 403, gunakan koneksi uji tanpa profile:read jika didukung publisher; jangan meminta izin dokumen sebagai pengganti.
  • Untuk 429, koordinasikan kondisi pembatasan resmi pada lingkungan uji. Jangan membanjiri produksi; batas kontrak adalah 60 permintaan/menit per koneksi dan pemeriksaan token per IP.
  • Untuk 503, publisher menyediakan kondisi gagal yang terkendali pada lingkungan live uji tanpa mengganggu pengguna lain. Jangan mematikan layanan produksi atau mengubah seluruh token untuk tes.
  • Jika suatu kondisi belum dapat diuji, isi “belum diuji/terhambat”. Jangan menggantinya dengan klaim lulus dari tes sintetis.

D. Pemeriksaan privasi

Pastikan route/helper baca profil tidak menulis profil ke DB dan tidak memanggil endpoint dokumen. Bila memeriksa log/observabilitas, gunakan alat privat yang tersanitasi; jangan mengaktifkan pencatatan body respons, header Authorization, cookie, ID pengguna, NIB, atau alamat.

7. Pemulihan dan pemeliharaan koneksi

  • Jika kepemilikan meragukan: jangan aktifkan pemetaan. Jika sudah aktif, nonaktifkan hanya koneksi terkait melalui operator; jangan mengalihkan akun tersebut ke token pemilik lain.
  • Jika akses harus dihentikan: hapus pemetaan terkait dan cabut token di Gustafta. Pastikan konfigurasi yang berjalan sudah diperbarui dan SBU tidak lagi menampilkan profil lama.
  • Rotasi: token berlaku 90 hari menurut kontrak. Buat pengganti profile:read milik pemilik yang sama, masukkan melalui Secrets, verifikasi, lalu cabut token lama. Jangan cetak token lama atau baru.
  • Setelah tes: cabut koneksi uji sementara, pulihkan konfigurasi yang disetujui, dan periksa ulang koneksi A/B yang memang akan digunakan.
  • Jika terhambat: laporkan langkah yang belum dapat dijalankan dan pihak yang perlu bertindak. Jangan menandai integrasi selesai hanya karena panduan atau checklist sudah dibuat.
